SECRETSIFT - PROJECT STRUCTURE
=============================

One-line summary
  secretsift plants FAKE ("synthetic") secrets into your app, runs your code, watches every place
  the secret could show up (logs, stdout, errors, HTTP, AI prompts, AI answers, files), checks
  each sighting against YOUR policy, and writes a report (terminal / HTML / JSON / JUnit).
  It runs locally. No server, no account, no frontend needed.

Numbers (generated from the real tree)
  Total files (excluding caches): 170
  Python lines of code, src + tests + examples: 11528
  Runtime dependencies: pydantic, pyyaml (nothing else). httpx and pytest are optional.

How a run works (read this first)
  1. secretsift.yaml            you describe: fake values, policy rules, scenarios (a Python function to call)
  2. config.py                 loads + validates the YAML (yaml.safe_load only)
  3. synthetic/generator.py    makes deterministic fake secrets (fake key, email, token ...)
  4. core/runner.py            for each scenario: fresh registry + event collector, then
  5. instrumentation/          switches on capture: logging, stdout/stderr, http.client, socket guard
  6.   your function runs      (optionally with a provider: mock / Ollama / OpenAI / Anthropic / Gemini ...)
  7. core/events.py            every observation becomes an Event (raw text stays in memory only)
  8. inspectors/               look for the fake secret in each event (raw + encoded variants)
  9. policies/                 decide ALLOW / WARN / DENY for each sighting (detection is not violation)
 10. core/analysis.py          turns DENY/WARN into Findings (deduplicated, with redacted evidence)
 11. reporting/                writes terminal, JSON, HTML (self-contained), JUnit XML
 12. cli.py                    exit code: 0 clean, 1 findings, 2 scenario errors only, 3 bad config/usage

Who does what (by package, under src/secretsift/)
  models.py            all shared data types (Event, Finding, Report ...). Raw secrets are never serialized.
  contracts.py         abstract interfaces (Inspector, Reporter, registry protocol)
  exceptions.py        error types; messages never contain secrets
  config.py            YAML config models + loader + starter config
  cli.py, __main__.py  the `secretsift` command (init, doctor, providers, validate, test, report, diff, demo, version)
  api.py               Python SDK: `with Drill() as d:` for use inside your own tests
  demo.py              built-in intentionally leaky / safe example functions
  synthetic/           fake value generation, secret registry, encoded-variant matching
  evidence/            redaction of evidence snippets and credentials
  instrumentation/     capture + guards (this is what "sees" the data)
  inspectors/          per-channel matchers (logs, errors, http, ai requests, ai outputs, storage)
  policies/            rule schema, compiler, evaluator, remediation hints
  core/                scenario spec, runner, analysis, lifecycle (cleanup), run context, event collector
  providers/           AI adapters + mock provider + instrumented wrapper (records prompts/answers)
  assertions/          assert_no_findings, baseline comparison (regressions)
  reporting/           terminal, JSON, HTML, JUnit, report diff, safe file writing (0600, atomic)
  integrations/        pytest plugin (fixture `secretsift`), optional httpx transport

Is there AI inside secretsift?
  No. Detection is deterministic: exact match plus listed encodings. AI apps are the thing being
  TESTED. AI providers are only adapters to send prompts. Everything works offline with the mock provider.
  Fixing a leak = editing your own application code at the component/location the finding names.
  secretsift gives static remediation hints; it does not rewrite your code.

How to extend (who can add what)
  New AI provider      subclass providers/base.py Provider, register in providers/registry.py
  New leak channel     subclass contracts.Inspector, add to inspectors/__init__.py default_inspectors()
  New policy           edit YAML only (policy.rules)
  New scenario         write a Python callable, reference it as "module:function" in YAML
  New report format    implement contracts.Reporter, register in reporting/__init__.py
  Use inside tests     api.Drill (any test framework) or the pytest fixture

Where things live outside src/
  tests/        unit/ (per package), integration/ (end to end + examples), security/ (redaction, escaping, offline guard)
  examples/     runnable examples, intentionally leaky + fixed versions
  docs/         DESIGN.md (binding design contract) and reference docs
  scripts/      verify.sh: one command that runs every check (tests, pytest plugin, lint, build, CLI, examples)
  .github/      CI workflows (tests, lint, typecheck, security), issue/PR templates

Run the tests (no pytest required)
  PYTHONPATH=src python3 -m unittest discover -s tests -t . -q
